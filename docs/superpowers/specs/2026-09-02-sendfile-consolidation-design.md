# Устранение двойной реализации sendFile

Дата: 2026-09-02

## Задача

В SDK было две независимые реализации метода Bot API `sendFile`, разошедшиеся за
время жизни репозитория:

| | `client/ym/files` | `client/ym/messages` |
|---|---|---|
| Путь | `/bot/v1/messages/sendFile` | `/bot/v1/messages/sendFile/` |
| Билдер мультипарта | `buildMultipartBody` | `buildSingleFilePayload` |
| Тело файла | `[]byte` | `io.Reader` |
| Уникальные параметры | `MimeType` | `ThreadID`, `SuggestButtons` |
| Разбор ответа | `{ok, message}` | `{ok, message_id}` |

Обе объявляли собственный идентичный `sanitizeFilename`. Именно это дублирование
скрыло недокументированное поле `caption` на всё время жизни репозитория
(исправлено в a8c89f8).

## Результаты проверки

### Форма URL: обе рабочие

Живая проба `botapi.messenger.yandex.net` без токена. Отсутствие токена здесь —
инструмент: 401 означает «маршрут найден, дошли до авторизации», 404 — «маршрута
нет».

| Запрос | Ответ |
|---|---|
| `POST /bot/v1/messages/sendFile` | `401 authentication_failed` |
| `POST /bot/v1/messages/sendFile/` | `401 authentication_failed` |
| `POST /bot/v1/messages/definitelyNotAMethod` | `404 resource_not_found` |

То же для `sendText`, `sendImage`, `sendGallery`, `getUpdates`. Сервер
нормализует хвостовой слеш. Расхождение в документации (слеш в заголовке URL,
без слеша в примере curl) отражает это безразличие, а не ошибку.

**Вывод: ни одна из двух форм не сломана; выбор чисто стилистический.**

### Настоящий дефект: `files` не мог работать

Документация `sendFile` описывает успешный ответ как
`{"ok": true, "message_id": 1647523230504005, "file_id": "<file_id>"}` — плоские
поля. У `sendText` то же; вложенного объекта `message` в Bot API нет.

`files/service.go` ожидал `{ok, message}` и возвращал `ErrInvalidResponse`, если
`message` отсутствует. Проверено подачей документированной формы ответа:

```
err = yandex-messenger: invalid response: ok=true message_present=false
```

`files.SendToChat` и `files.SendToLogin` не могли завершиться успешно против
живого API ни разу. Тесты пакета проходили только потому, что подавали
выдуманный ответ, которого API не отдаёт.

Сопутствующее: `files/doc.go` рекламировал несуществующую сигнатуру
(`SendToChat(ctx, chatID, "report.pdf", fileReader)`); у пакета не было ни одного
потребителя, кроме поля `YMClient.Files`.

## Решение

Пакет `client/ym/files` удаляется целиком. Репозиторий на `v0.1.1`, semver
допускает ломающие изменения в `v0.x`; работоспособных потребителей у пакета нет
по определению — он никогда не работал.

Удаление снимает сразу весь класс расхождений: вторую форму URL, второй билдер
мультипарта, второй `sanitizeFilename`, фиктивный контракт ответа и
депрекированное `Caption`.

Единственная возможность, которой владел только `files`, переносится в
`messages`: `SendFileRequest` получает поле `MimeType`, задающее `Content-Type`
части `document`. `ThreadID` и `SuggestButtons` там уже есть, поэтому
объединённый API покрывает обе стороны.

Отдельная константа эндпоинта не вводится: после удаления путь `sendFile`
встречается ровно в одной точке. Константа на одну точку использования — это
индирекция без выигрыша.

## Объём работ

1. Удалить `client/ym/files/` (`service.go`, `doc.go`, `service_test.go`).
2. Убрать импорт и поле `Files` из `client/sdk.go`.
3. Добавить `MimeType` в `messages.SendFileRequest` и параметр `mimeType` в
   `buildSingleFilePayload`; `SendImage` передаёт пустую строку.
4. Тесты: MimeType попадает в `Content-Type` части `document`; при пустом
   значении заголовок не ставится; регрессионный тест на документированную
   плоскую форму ответа.
5. Документация: `README.md`, `README.en.md`, `CLAUDE.md`, `.github/PROMOTIONAL.md`.
   `CHANGELOG.md` — новая секция `Removed` в `[Unreleased]`; историческая запись
   выпущенной версии не переписывается.

Тесты удалённого пакета не переносятся: они закрепляли неверный контракт ответа,
и перенос перенёс бы заблуждение. Новый регрессионный тест берёт форму ответа из
опубликованной документации.

## Дополнение: полное покрытие спеки

Изначально полнота параметров была вынесена за объём. По отдельной просьбе она
сделана в этой же ветке.

Разрыв был одинаков у всех четырёх методов отправки: ни один не поддерживал
`message_id` (редактирование), `reply_quote`, `forwards` и `action_buttons`, а
мультипарт-методы вдобавок не поддерживали `reply_message_id`,
`disable_notification` и `important`. Ответы теряли `file_id` у `sendFile`,
`file_id`/`width`/`height` у `sendImage` и массив `images` у `sendGallery`.

Сделано:

1. Типы `ym.Forward`, `ym.ActionButtons`, `ym.ActionButton`,
   `ym.ActionButtonIcon` и константы иконок.
2. Общая структура `attachmentCommon` и единственный писатель полей
   `writeCommonFields`. Именно расхождение наборов параметров по методам было
   исходной болезнью, поэтому набор теперь ровно один.
3. `buildSingleFilePayload` переведён на структуру: восьми позиционных
   аргументов уже хватало для ошибки перестановки, а спека добавляла ещё семь.
4. Результаты возвращаются через существующие поля `ym.Message` —
   `Document`, `Image`, `Gallery`. Новые типы результата не понадобились, и
   сигнатуры не сломаны.
5. Документированные ограничения проверяются до отправки: `reply_quote` требует
   `reply_message_id`; `forwards` несовместим с `reply_message_id`; не более 6
   action-кнопок, 100 suggest-кнопок и 6000 символов текста галереи.

## Остаётся вне объёма

- `updates/service.go:41` использует `getUpdates` без слеша — при доказанном
  безразличии сервера это косметика в другом сервисе.
- `ym.SuggestButtons.Buttons` объявлен как `[][]InlineSuggestButton`, тогда как
  спека допускает и плоский массив при `layout: "false"`. Поддержка обеих форм
  требует своего маршалера и меняет публичный тип, поэтому вынесена отдельно.
- `sendText` документирует устаревший `inline_keyboard`; он намеренно не
  добавляется — спека помечает его deprecated.
